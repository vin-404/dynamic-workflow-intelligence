# Decisions

Judgement calls made during the autonomous refactor. One line of reasoning
each. Newest phase last.

Rule applied throughout: when ambiguous, choose the option that is **smaller,
more reversible, and closer to `docs/ARCHITECTURE.md`**.

## Phase 2

| # | Decision | Reasoning |
|---|---|---|
| D-17 | The registry is a function returning a tuple, not a decorator writing into a module-level list | `core/` holds no mutable module state, enforced by the purity test, and that is the precondition for evaluating optimizer candidates concurrently. A decorator would need a mutable accumulator. Adding a detector is still one line. |
| D-18 | Delete `accuracy.precision_vs_planted`; label **every** finding both fixtures contain and report `recall`, `precision`, and `planted_recall` separately | The prototype's metric punished the detectors for being right. Three planted faults were labelled; Phase 2 legitimately finds eleven real problems in that fixture, so `precision_vs_planted` would have read 33% while nothing was wrong. Labelling all eighteen findings across both fixtures (with a description each, and a `planted` flag preserving the original demo story) makes both numbers mean what they say, and turns the fixtures into a strict regression lock. |
| D-19 | A cyclic workflow makes `evaluate()` return `schedulable=False` plus a `dependency_cycle` finding, instead of raising `CycleError` | An exception is a worse answer than a finding: the UI can render the cycle, point at it, and stay up. `schedule()` still raises for direct callers, so the existing cycle-detection test is untouched. |
| D-20 | `Impact` carries `magnitude_kind` (`observed_delay_days` vs `exposed_days`) rather than reusing `attributed_delay_days` for Tier-0 findings | At Tier 0 nothing has been lost yet — the magnitude is work *exposed* to a structural weakness. Calling that a delay would be the quiet kind of dishonesty the whole brief is written against. Renaming the field is the smaller cost. |
| D-21 | `ready_but_idle` is declared Tier 2 (historical), not Tier 1 as ARCHITECTURE D.1's table has it | The tier is a *data requirement*, and this detector ages a task from when its last predecessor's status transition was recorded. With no event log that age is measured from day 0, so it would report every unstarted task on every fresh project. ARCHITECTURE D.1's table wins on design intent; this is a factual correction to which tier the detector needs. |
| D-22 | Add `projected_vs_planned_finish` (Tier 1) and `isolated_task` (Tier 0) beyond the prompt's explicit list | Both are in ARCHITECTURE D.1's table — "projected vs planned finish" and "orphan/unreachable tasks". The first is the headline number a delivery lead asks for, stated as a finding with its arithmetic attached rather than only as a top-level `slip_days`. |
| D-23 | `unavailable_checks` includes five `PLANNED_CHECKS` marked `(not built yet)` | Without them the Tier-3 gap lists nothing, which implies cross-project calibration becomes available once you have history. It does not — nothing collects cross-project actuals. Showing the roadmap in the payload is more honest than an empty gap. |
| D-24 | `zero_slack_chain` uses a configurable `critical_share_threshold`, default 0.6, rather than a hardcoded 0.5 | 50% of tasks being critical is common and unremarkable; my first threshold fired on a workflow with three tasks holding nine days of slack each. Two thirds is a plan with no shock absorber. Making it config, echoed in the evidence, means the number is reviewable rather than mine. |

## Phase 3

| # | Decision | Reasoning |
|---|---|---|
| D-25 | `inverse()` returns `tuple[Mutation, ...]`, not a single `Mutation` | Undoing a task removal is not one step: it re-adds the task, restores each edge with its `dep_type` and `consumes` flags, drops the bridges the removal created, re-attaches assignments, and re-links consumed requirements. A single-mutation inverse looked tidier and produced two silent round-trip failures. The signature should admit what is true. |
| D-26 | `TASK_DELAY_ADD` writes a separate `TaskSpec.added_delay` rather than raising `effort` | The fixture's stalled approval is nine elapsed days against a two-day estimate, so raising the estimate to seven changed the schedule not at all - the observed duration already exceeded it. A delay has to sit on top of what a task already looks like it will take. Keeping the two apart also means a slip reads as slip in `slip_days` rather than as a quietly re-baselined plan. |
| D-27 | Three mutations gained an optional "set" form (`RESOURCE_UNAVAILABLE_WINDOW.windows`, `TASK_DELAY_ADD.total_delay_days`, `REQUIREMENT_VERSION_BUMP.version_no`) instead of three new mutation kinds | Each exists only so the mutation's inverse is exact. Three extra kinds used by nothing but undo would take the algebra to twenty to save three optional fields, and would weaken the "seventeen kinds, closed" claim for no gain. |
| D-28 | `evaluate()` returns `schedulable=False` plus a `dependency_cycle` finding for a cyclic scenario, and `simulate()` returns the base evaluation plus the rejection for an invalid one, rather than raising | A UI needs to render "here is where you are, and here is why we will not do that". An exception gives it nothing to draw. |
| D-29 | `POST /projects/{id}/what-if` validates before writing anything and stores no row when `keep=false`; `POST /scenarios` stores an invalid scenario with `status="rejected"` and the reason | Two different needs. A throwaway question should leave no trace and must return the *structured* rejection - the cited constraint and the reason on record - because "M09 is mandatory" is much weaker than "M09 is mandatory because UN38.3 certification is a legal precondition to shipping". A deliberately created scenario should survive its own rejection so the user can read and edit it, which is also exactly what Phase 7 needs for LLM proposals. |
| D-30 | `to_canonical()` sorts set-like fields (`consumed_by`, `skills`, `required_skills`, `working_days`, `holidays`, `unavailable_windows`) | Their order carries no meaning, so two snapshots differing only in insertion order must hash the same. Found by a round-trip that produced an identical workflow with a different hash - which would have broken version comparison and the immutability guarantee, not just undo. |
| D-31 | `services/scenarios.get_row` uses `populate_existing=True` | The session is configured `expire_on_commit=False`, so an already-identity-mapped `Scenario` kept the `mutations` collection it was first loaded with and an appended mutation was invisible. A real bug, not a test artefact. |

## Phase 4

| # | Decision | Reasoning |
|---|---|---|
| D-32 | Risk is computed inside `evaluate()` rather than as a separate on-demand call | It is pure arithmetic over the schedule that call already produced, so it costs nothing extra, and it means one `analyze` round trip answers Capabilities 1 and 2 together. A separate call would have meant a second schedule pass for the same numbers. |
| D-33 | The `likely` run of the three-point range **is** the headline projection, not a separately computed estimate | Otherwise the middle of the range is a fourth number that does not match the one shown everywhere else, and the first question anyone asks is which of the two is real. |
| D-34 | `criticality_proximity` is rank-based, and `resource_pressure` measures the roll-up resource as well as the assignee | A pure slack ratio would duplicate `slack_ratio`; a rank distinguishes "third-tightest of seventeen" from "already critical". And a person with one task whose *team* is at capacity is genuinely under pressure - measuring only the person would miss the seeded marketing bottleneck entirely. |
| D-35 | The no-probability test asserts **substance, not vocabulary** | Banning the word "probability" is the wrong test once the payload is honest: it says "not a probability" four times, names a flag `is_probability`, and has a field called `what_would_make_this_a_probability`. A word-ban either fails on those denials or accumulates per-key exceptions until it proves nothing. The replacement walks the whole payload and fails if any key named like a likelihood holds a *number*, and separately checks that no sentence a user reads makes a probability claim. That catches the real failure mode. |
| D-36 | A factor that cannot be measured reports `available: false`, contributes 0, and is listed in the assumptions - rather than being imputed or silently dropped | Imputing it would invent evidence; dropping it would change the score's scale without saying so. Reporting zero with a reason keeps the arithmetic honest and tells the user what would unlock the factor, which is the same contract the detector tiering uses. |
| D-37 | Band thresholds (0.55 high, 0.30 moderate) are labels on a continuum and `band` is never returned without `score` | The cut points are arbitrary and admitting that is cheaper than defending them. Any UI that shows the band must show the number beside it. |

## Phase 5

| # | Decision | Reasoning |
|---|---|---|
| D-38 | Add `gen_drop_bottleneck_tasks`, a sixth generator, opt-in behind `aggressive=True` | The five deterministic generators are all restructurings, so none of them ever proposes deleting a task - which means the constraint gates never fire and the refusal beat is unreachable. An optimizer that never proposes the cheat never demonstrates that it will not take it. It is also the honest answer for a user who has marked nothing mandatory: cutting scope is a real option. |
| D-39 | The constraint gates follow task **lineage** through splits and merges | The first version refused `Split T02 across 2 people` with "this candidate drops T02 -> T03", which is false: the split rewires the edge to both parts and the ordering survives. A misleading refusal is worse than no refusal, because it teaches the user to distrust the ones that are real. A genuine deletion is still refused, and that is tested so the leniency cannot become a loophole. |
| D-40 | Return **two** recommendations: the top scorer, and the top scorer that does not change scope | `TASK_REMOVE` is on the brief's own justified list for the effort-conservation gate, so a permitted deletion can legitimately outrank every restructuring. Presenting only the winner would make "do less work" look like an engineering result. Presenting both makes it a scope decision, which is the user's to make and not the optimizer's. |
| D-41 | The time budget is a caller-supplied `should_stop` callable, not a clock read inside `core/` | Keeps the purity invariant literal - `core/` may not import `time` - and makes the budget test deterministic instead of a race against a real timer. The clock is already an argument everywhere else; this is the same rule. |
| D-42 | The base workflow is evaluated once and shared across candidates, rather than each candidate going through `simulate()` | `simulate()` evaluates base and candidate, so N candidates would cost 2N evaluations for N identical base results. Sharing it halves the work and is asserted by a test that counts the calls. The comparison payload is still `simulation._compare()`, so an optimizer candidate and a hand-written what-if produce the same shape. |
| D-43 | Surviving candidates are persisted as real `Scenario` rows by default | It is what lets the UI diff, edit or apply one without re-running the search, and it means there is no special apply path for an optimizer result - the existing scenario endpoints already work on it. `persist_candidates: false` turns it off for a throwaway comparison. |

## Phase 7

| # | Decision | Reasoning |
|---|---|---|
| D-49 | `anthropic==1.4.0` is a **listed** requirement, not an optional extra, even though the default provider is `NullProvider` | An optional dependency that is never installed is a dependency that is never tested. Listing it means the SDK contract tests actually run, which is what catches a breaking SDK change before a demo does. The import stays lazy, so the application and the whole suite still work without it — the property the brief asks for is preserved without paying for it in coverage. |
| D-50 | Three roles, three prompts, three schemas — never one prompt that does all three | They fail differently and want different repair strategies: a bad interpretation is a misread sentence, a bad proposal is a wasted candidate, a bad narration is a false number. One mega-prompt makes every failure the same failure and gives the model authority over all three at once. |
| D-51 | The no-write-path guarantee is enforced by **parsing the AI modules**, not by a convention or a code review note | A convention holds until someone imports a service to "just look something up". The test reads every file under `ai/` and fails on a forbidden import or a `.commit()` call, so the guarantee survives the next person who does not know it exists. Same technique as the `core/` purity test, for the same reason. |
| D-52 | A narration containing a number the engine did not produce is **discarded**, not flagged | Flagging it puts the burden on the reader to notice a warning next to a confident sentence, which is exactly the failure this rule exists to prevent. Throwing it away and showing the engine's own wording costs a nicer paragraph and buys a guarantee that holds without the user's attention. The reason is still shown, because a visible discard is more trustworthy than a silent one. |
| D-53 | A numeric token glued to letters is an **identifier, not a quantity** — on both sides of the check | Found by the tests: `T03` in the payload made "3" an available number, so a narration claiming "3 days saved" would have passed verification. Task keys are everywhere in the payload, so nearly every small integer was silently licensed. Requiring the number to stand alone fixes the payload side; applying the same rule to the narration means "T03 is the bottleneck" still passes, which is the sentence a narrator actually wants to write. |
| D-54 | The projection has a **hard task ceiling** on top of the per-finding cap | Compaction was defeated by volume rather than by one wide finding: 300 isolated tasks produce 300 findings, each naming one task, and together they named everything. Capping findings considered (12) and tasks per finding (5) fixes that case; the ceiling makes it structural rather than a fix for one shape. The critical path is kept whole and the remaining slots go to the tightest slack, deterministically — so the prompt hash stays stable and the cache keeps working. |
| D-55 | The Proposer is a **third candidate source** in `services/optimization.py`, not a parallel path with its own scoring | Its proposals go through the same semantic validation, the same seven constraint gates and the same six-criterion scoring as the six deterministic generators. A model proposal that wins, wins on the same table everyone else is scored on; one that breaks a constraint comes back refused with the constraint cited. Giving the model its own path would make "the AI suggested it" a reason, and it is not one. |
| D-56 | With no model, the Interpreter falls back to a **labelled pattern matcher** rather than a flat refusal | A flat refusal is simpler and would have been defensible. But the demo has to run with the LLM disabled, and "type a sentence" that always fails is worse than no box at all. The matcher handles the same four shapes the what-if form offers and refuses everything else, and both the API (`method`) and the UI ("matched by pattern (no model configured)") say what produced the answer. The rule it must not break — never guess — is intact; it just does its guessing in public. |

## Phase 8

| # | Decision | Reasoning |
|---|---|---|
| D-57 | Add a tenth Tier-0 detector, `critical_path_single_owner`, in Phase 8 rather than noting the gap and moving on | The demo walk found it: ARCHITECTURE Section I's cold-start beat names "one person on three zero-slack tasks", and no detector said that. `resource_overallocated` structurally cannot - a strictly sequential chain never asks for the resource in two places at once, so capacity is never exceeded and the plan looks fine. It is not fine: a critical path owned end to end by one person has no redundancy at all. The detector defers to `unassigned_critical_task` when somebody is missing, and stays quiet for a team resource with more than one member, because a team can absorb an absence and a person cannot. |
| D-58 | The risk score is serialised as the sum of the **rounded** contributions, not as the rounded sum | Found by running the demo walk twice: the factor column added up to 0.6298 while the headline read 0.6299. The product's claim is "add the column up yourself" - a reader who does that and gets a different number has caught the system being loose with arithmetic, and every other honest number on the screen becomes suspect. Rounding once, at the point of display, costs at most half a thousandth of ranking precision and makes what is on screen exact. |
| D-59 | The "LLM enabled" rehearsal runs against a **recorded provider**, not a live API | No `ANTHROPIC_API_KEY` exists in the repository or the environment, and the brief names a missing credential as a stop condition. Halting the whole run over it would be wrong - the credential is needed for one *verification*, not for the product, which is designed to work without it. So the enabled path is exercised end to end with replayed structured output: the plumbing, the validation, the gating, the caching and the number check all run for real. What has never run is a live model call, and that is stated as a risk rather than papered over. |
| D-60 | `demo_check` asserts what each beat **claims**, not that each endpoint returns 200 | A smoke test that walks the same path would have passed while the cold-start beat had nothing to say about the single owner, while the factor column did not add up, and while a stale narration number went uncaught. Each of those was found by asserting the sentence the presenter says out loud. The script is the rehearsal, in a form that fails. |

## Phase 9

| # | Decision | Reasoning |
|---|---|---|
| D-61 | `CORS_ORIGINS` accepts a **comma-separated list**, and `*` is refused at startup | A hosting dashboard gives you a single-line text box; quoting a JSON array in one is how you end up with a deployment that has no CORS and a frontend that renders an empty page. The JSON form still parses, so an existing deployment does not break. `*` is refused rather than accepted because this API allows credentials, and a wildcard with credentials is rejected by every browser - accepting it would produce something that looks configured and behaves like a blocklist. |
| D-62 | `Annotated[list[str], NoDecode]` on `CORS_ORIGINS` | Found by testing the thing I had just written: pydantic-settings JSON-decodes complex fields from the environment *before* any validator runs, so the comma-separated form died with a `JSONDecodeError` at import time - the application would not start at all. `NoDecode` hands the raw string to the validator. |
| D-63 | Structured errors pass the **detail through untouched** rather than flattening it to a string | `{rejections: [{constraint, constraint_reason, ...}]}` and `{cycles: [...]}` are the product. A middleware that turned those into `"detail": "mutation 1: ..."` would throw away the only part of a refusal a user can act on, which is exactly the thing this system is built to preserve. The wrapper adds `error`, `hint` and `request_id` around it and touches nothing inside. |
| D-64 | `/health` does **not** touch the database; `/ready` does | They answer different questions and platforms use them differently. A liveness probe that fails when the database blips gets the container killed and restarted, turning a recoverable outage into a crash loop. Splitting them also makes the most common deployment failure self-diagnosing: `/health` passing and `/ready` failing means `DATABASE_URL` is wrong, and `docs/DEPLOY.md` says so in those words. |
| D-65 | The request deadline is a **backstop**, and the optimizer's real budget stays the injected `should_stop` | `asyncio.wait_for` cannot interrupt synchronous CPU work; it frees the request and the computation finishes on its own. That is acceptable for pure, finite, lock-free work, and it is honest to say so in the module rather than imply a hard kill. The mechanism that should actually fire is the one inside the search, which stops between candidates and returns the partial ranking it already has - measured at 11 ranked candidates in 136ms against a 0.1s budget. |
| D-66 | The picked identity is sent as `X-User-Id` and **never checked** | It drives `created_by` and the member list, and nothing else. A missing, malformed or stale id is served identically to a valid one, because refusing a request over it would be enforcing an identity - which is authentication, which is explicitly out of scope. A test asserts that `/api/login`, `/api/auth` and friends do not exist, so adding one has to be a deliberate act. |
| D-67 | `POST /admin/reset-seed` is **disabled** when no `ADMIN_TOKEN` is set, rather than open | An unguarded database reset on a public URL is an undo button for your demo that anyone on the internet can press. Disabled-by-default means the safe configuration is the one you get by doing nothing. The comparison is `hmac.compare_digest`, because comparing a secret with `==` leaks its length and prefix to anyone patient enough to measure. |
| D-68 | Every stage gets **its own** error boundary, keyed on the stage | One boundary around the whole app would mean a bug in the dependency graph blanks the findings above it. Per-panel boundaries cost the user the panel and not the session, and the graph gets its own because it is the only thing on screen with a third-party layout engine underneath it. Keying on the stage clears a failure when the user moves on, so one broken panel cannot poison the nav until a reload. |
| D-69 | The walkthroughs move into `frontend/e2e/` with `playwright` as a devDependency | Carried from Phase 6's recorded risk: verification that lives in a scratch directory is verification nobody else can run. They also needed a shared `signIn` helper the moment the name picker became the first screen - which is itself the argument for keeping them in the repo, where a product change breaks them visibly instead of silently. |
| D-70 | The frontend gets its own `.dockerignore` | Its build context is `./frontend`, so the repo-root file does not apply. Without it, `npm ci` copies a host-built `node_modules` into the image and the build fails in a way that looks like a dependency problem and is not. |
| D-71 | The optimizer's spinner names the stage on a **timer**, and the timer is deliberately slower than the search | The search is one request, so the client genuinely cannot know which stage the server is in. Advancing labels every 700ms against a search that finishes in about 300ms means the label never claims to be further along than it could be - it stops on the last stage and waits. The alternative, streaming real progress, would mean a websocket for a third of a second of work. |
| D-72 | `docs/DEPLOY.md` supersedes the untracked `deploy-kit/` draft, which is left in place rather than deleted | The draft was user-supplied and mostly right; two things in it were stale (a `COPY engine.py` that Phase 1 removed, and `CORS_ORIGINS` documented as a JSON array, which is now the secondary form). It is untracked working material that is not mine to delete, so it stays and `docs/DEPLOY.md` is the one the repository points at. |

## Phase 10 — authentication

Phase 9 shipped an identity nobody checked and said so plainly (D-66). This
phase replaces it with a Google session and makes `ProjectMember.role`
enforced. The one architectural idea everything else follows from: the browser
only ever talks to the Next.js origin, so Auth.js runs in Next, the session
cookie is same-origin, and Next injects identity into the upstream request.

| # | Decision | Reasoning |
|---|---|---|
| D-73 | Identity is injected in `src/proxy.ts` via `NextResponse.rewrite(upstreamURL, { request: { headers } })`, and the `/api/:path*` rewrite is **deleted** from `next.config.ts` rather than kept as a fallback | `rewrites()` is static configuration: it runs per request but cannot read the session cookie, so it can never say who is asking. The proxy already has to run for page protection, and the rewrite hands the request to Next's own streaming proxy, so method, body and response pass through verbatim for free — a route handler would mean hand-rolling `duplex: 'half'`, method fan-out and header filtering. Keeping the config rewrite as a fallback would have been worse than deleting it: it is precisely the path a request takes when it slips past the matcher, and it reaches FastAPI with no identity and no secret. One door is the point. |
| D-74 | The file is `src/proxy.ts`, not `middleware.ts`, and not at the project root | Next 16 deprecated the `middleware` convention and renamed it `proxy`, function name included; `middleware.ts` still works but warns, and having both is a hard build error. The location is not cosmetic: Next scans only the directory beside `app`, so a root `proxy.ts` under a `src/app` layout is **silently ignored** — the build succeeds, `middleware-manifest.json` comes out empty, and nothing is protected. Found by reading the manifest, because nothing warns. |
| D-75 | The proxy matcher is two entries: a bare `/api/:path*`, and a negative-lookahead pattern for everything else | The matcher every tutorial copies begins with a negative lookahead on `api`, which removes `/api/*` from the proxy and leaves identity injection nowhere to happen. And the asset-extension exclusions the page pattern needs would punch a `/api/anything.png` hole straight through to the backend. Listing `/api` separately, with no exclusions, closes both. |
| D-76 | Both `X-User-Id` and `X-Proxy-Secret` are deleted from every incoming request before ours are set — including when no secret is configured, and including on page requests | This is the entire security property. A browser that sends its own `X-Proxy-Secret` and gets it forwarded makes the design *worse* than no auth, because the backend would then trust it. Next's `x-middleware-override-headers` replaces the header set rather than merging it, so anything absent from the forwarded `Headers` is dropped upstream. Asserted against a real build with a spoofing client, not reasoned about. |
| D-77 | Sessions are JWTs with **no database adapter** | The backend already owns user rows; a Next-side copy would be a second source of truth about who someone is. It also lets the proxy decide whether a request is authenticated without a database round trip on every prefetch, which matters because the proxy runs on every route. |
| D-78 | A failed backend upsert **fails the sign-in** (`?error=AccessDenied`, no cookie minted), with a self-healing retry in the `jwt` callback as a second layer | The failure mode to avoid is a session with no backend id: the user sees a logged-in app while every request they make is anonymous, and everything they create belongs to nobody. Failing at sign-in is the only point where there is a page to put a readable sentence on. `AccessDenied` specifically, because Auth.js forwards only a fixed allow-list of error codes to the client and a custom one degrades to "Configuration". |
| D-79 | The walkthrough Credentials provider is gated on `E2E_AUTH_ENABLED=1` **and** `NODE_ENV !== "production"`, and is not constructed at all when either fails | Google's consent screen cannot be driven headless, so `npm run e2e:all` needs a door — but a password-free sign-in a deployment can be talked into using is not a door, it is a hole. Because Next inlines `NODE_ENV` at build time, the guard is statically false in any `next build` output: the provider *cannot exist* in a production bundle, which is stronger than checking at runtime. The accepted cost is that the walkthroughs must run against `next dev`, which is what `e2e/README.md` already prescribed. |
| D-80 | Auth.js's own endpoints stay mounted at `/api/auth/**` rather than moving to a non-`/api` prefix | Keeping the default `basePath` means `NEXTAUTH_URL`, the callback URLs registered with Google, and every Auth.js client helper all work unconfigured. The proxy exempts the prefix explicitly and filesystem routes are matched before `afterFiles` rewrites, so it never reaches FastAPI — verified: `/api/auth/nope` returns Auth.js's own 400, not a proxied 404. |
| D-81 | `backendUserId` is declared by augmenting `@auth/core/types` and `@auth/core/jwt`, not `"next-auth"` | The Auth.js docs say to augment `"next-auth"`, but `next-auth` only *re-exports* those interfaces. Declaring them under `"next-auth"` creates a second, shadowing interface that Auth.js's own callback signatures never see — the field would type-check at the call site and be missing everywhere it actually matters. |
| D-82 | The API trusts a **header pair**, `X-User-Id` plus `X-Proxy-Secret`, and nothing else. **Supersedes D-66.** | D-66 was right for a name picker on a shared demo and wrong the moment a real session exists: an identity nobody checks is fine when nothing is protected, and is impersonation-as-a-feature when a role is. Putting the login in FastAPI would have meant sessions, callbacks and a second place to get CSRF wrong, next to the framework that already does it; putting it in front means this service verifies one secret and keeps its whole surface stateless. Rejected: verifying a JWT here — it moves the same trust decision into key rotation and clock skew for no gain, because the proxy is the only thing that can reach the API anyway. `hmac.compare_digest`, for D-67's reason. There is still no login route in FastAPI, and the test asserting so stays green. |
| D-83 | `PROXY_SHARED_SECRET` **unset means the pre-auth behaviour, unchanged** — the header trusted as sent, no role enforced, anonymous served | The 780 tests that existed before this phase are all written against the open instance, and so is a fresh clone with no `.env`. Treating the closed configuration as the default would have meant editing hundreds of tests to add a header, which is how a permission layer gets merged with its own regression net rewritten to agree with it. One switch, off by default, means the compatibility path *is* the default path and is exercised on every single run rather than remembered. |
| D-84 | Enforcement is **one router-level dependency that refuses by default**, not a decorator per write route | A per-route `Depends(require_editor)` is one commit away from a new write endpoint nobody annotated, and that failure is silent: the endpoint works, for everybody, and no test fails. So the guard is attached to the router, everything that is not a `GET` needs `editor`, and the only escape is an explicit `(method, path)` entry in `deps.READS_THAT_POST`. Adding a write inherits the guard; exempting a read is a reviewable line in one file. Two tests walk every route in the application and fail on an unguarded write or a stale exemption — in the spirit of `test_core_purity`, and they had to recurse through FastAPI 0.141's lazy router inclusion, because `app.routes` is no longer flat and a test that iterated it would quietly assert nothing. |
| D-85 | A role protects **authorship, not visibility**: reads stay open to anonymous and non-member requests alike | This product has never been multi-tenant. `GET /api/projects` lists every project to everybody and a Phase 9 test asserts two people see the same project, so member-only reads would either break that test or contradict the endpoint next to it. The rejected alternative — 403 on read for a non-member — is a tenancy model, not a permission fix, and it would break "send a colleague the link", which is what the sharing story is for. What is protected is the thing that was actually at risk: a stranger changing your plan. |
| D-86 | A **viewer may evaluate, optimize and ask a what-if**; the line is "does it move `project.current_version_id`" | A read-only seat that cannot ask "what happens if this slips" is a screenshot, and Capability 3 is the product. Drawing the line at HTTP method would have refused `POST /analyze`; drawing it at "writes any row" would have refused `evaluate`, which writes an `AnalysisRun`, and `optimize`, which writes candidate `Scenario` rows. Both are scratch paper — checked, not assumed: no service behind analyze, risk, optimize, interpret or explain contains `write_version`, `ensure_draft` or an assignment to `current_version_id`. `apply` is the one endpoint that does, and it is squarely a write. |
| D-87 | `POST /api/seed/reset` inherits `ADMIN_TOKEN` the moment a deployment authenticates | It is `POST /admin/reset-seed` without the token — the same total destruction through a second door, and it predates the guarded one. Disabling it outright would break the local reset `docs/PROGRESS.md` sends developers to, so it follows the same one switch as everything else: untouched with no `PROXY_SHARED_SECRET`, behind D-67's token once there is one. Merely being signed in is deliberately not enough — no ordinary user should be able to drop every project on the instance. |
| D-88 | `NEXT_PUBLIC_API_URL` is **removed from the codebase**, not documented as "must be empty". `src/lib/api.ts` hard-codes a relative base | Found during integration, and it would have made the whole phase decorative. `api.ts` read that variable as its base URL, and `docker-compose.yml` and `frontend/Dockerfile` both *defaulted* it to an absolute backend URL. With it set, the browser calls FastAPI directly, cross-origin — past the Next origin, past the session check, past the header injection — and the app looks signed-in while every request arrives anonymous. Documenting "leave this blank" would have made the safe configuration the one you get by remembering. Deleting the variable makes it the only configuration there is. The backend URL is now server-side only (`API_REWRITE_URL`), which also means re-pointing the frontend is a restart rather than a rebuild. |
| D-89 | The proxy sends `X-User-Id` **unconditionally** and only `X-Proxy-Secret` conditionally | The two headers are not symmetrical and the first draft treated them as one, sending neither unless a secret was configured. Both auth agents independently flagged the consequence: the backend still trusts a bare `X-User-Id` in open mode, so withholding the identity there protects nothing and instead makes `created_by` come back null with no member row — ownership silently disappearing in exactly the configuration a developer runs locally. The session has already been verified by the time the header is set; the secret's only job is to prove to the backend that the header came from us, and where the backend is not asking for that proof there is nothing to withhold. |
| D-90 | `backend/tests/conftest.py` pins `PROXY_SHARED_SECRET=""` before the app is imported | Same technique and same reason as the existing `DATABASE_URL` pin (D-06). `Settings` reads `env_file=".env"`, so a developer who put a real secret in the repo-root `.env` would silently flip the entire suite into enforcing mode, and the tests asserting the open behaviour would fail on their machine and nowhere else. An explicitly empty environment variable outranks the dotenv value — verified — so the compatibility path is the one the suite always runs, and `test_auth.py` sets the secret per-test on the live `settings` object to cover the other half. |
| D-91 | The name picker is **deleted**, and the walkthrough asserts its honesty copy is *gone* rather than just dropping the assertion | `WhoAreYou.tsx` promised "there is no login here", "no password needed" and "anyone with this link can pick any name". Every word was true and every word is now false, so leaving the component as a fallback would have left a second, unenforced identity next to the real one — a user could name themselves twice and the second would be ignored. The browser walkthrough now asserts that copy is absent, so a revert cannot quietly restore a false promise. What replaces it is a claim the picker could never make, and which the walkthrough also asserts: a signed-out request to `/api/*` is refused with a 401 in the standard envelope. |

## Phase 10 — the design system

| # | Decision | Reasoning |
|---|---|---|
| D-92 | Base `radix`, style `nova`, via `npx shadcn@latest init --base radix --preset nova` | The task requires `sonner`, and the skill's own rule is that Base UI projects use the `toast` component while Radix projects use `sonner` — choosing `base` would have made the required toast library the wrong one for the project. Radix's `asChild` is also the composition idiom the wave-2 agents are most likely to already know. |
| D-93 | Legacy `--color-accent` keeps the brand blue; the shadcn `accent` role loses to it, and `select.tsx`'s focus highlight moves to `muted` | The two vocabularies collide on exactly one name: legacy `accent` is a saturated blue used as `text-accent` and `bg-accent text-background`; shadcn `accent` is a subtle hover surface. Only one can own `bg-accent`. Letting shadcn win would have turned every `text-accent` near-invisible and every primary button grey-on-dark across twelve panels — a silent mis-render, not a build failure. Letting legacy win costs one line in `select.tsx`, the only one of the fourteen primitives that referenced `accent` at all. Rejected: renaming the legacy token, which means editing the twelve panels wave 1 is forbidden to touch. |
| D-94 | `--primary` is a strong neutral, not the accent | The brief reserves one accent for critical path and high-severity findings. If `primary` were the blue, every default shadcn button would be blue and the reservation would be meaningless within a day. Muted neutrals carry actions; the accent carries meaning. |
| D-95 | Dark mode is a `@media (prefers-color-scheme: dark)` branch on `:root:not(.light)` **in addition to** shadcn's `.dark` class variant, with `@custom-variant dark` rewritten to match both | shadcn ships class-only dark mode and documents `next-themes` as the switch, which needs a provider in `layout.tsx` — a file that agent did not own, and a provider would be a feature the brief excludes. Class-only would have rendered the app light-on-light regardless of the user's system preference, which is the exact catastrophic regression wave 1 had to avoid. Keeping both branches means a future `next-themes` toggle drops in and wins without touching the CSS again. |
| D-96 | Derived aliases (`--card`, `--muted`, `--red`, and the rest) are declared on `:root, .light, .dark` rather than once on `:root` | A custom property whose value contains `var()` is substituted at computed-value time on the element that declares it. Declared only on `:root`, `--card: var(--panel)` would resolve against `:root`'s raw values, and a `.dark` class placed on anything but the root element would inherit an already-substituted light colour. Repeating the alias block on every mode-bearing selector costs nothing and removes a failure mode nobody would find by reading the file. |
| D-97 | Severity is three named tokens — `severity-high`, `severity-medium`, `severity-low` — set to the same values as the existing `red`/`amber`/`green`, which survive as aliases | Naming the states rather than the hues is what makes a fourth one hard to add: there is no `severity-info` to reach for. Setting them to the existing values makes wave 2's migration a rename with no visual diff, so a mis-mapped severity shows up as a wrong word rather than a wrong colour. `violet` stays defined because `OptimizePanel` still names it, and is documented as not a severity. Rejected: deleting `violet`, which breaks a component wave 1 may not edit. |
| D-98 | Tabular numerals are a base rule on `body`, not a utility wave 2 must apply | The brief asks for tabular figures everywhere a number appears; in this app that is everywhere. A utility is something each agent has to remember on each cell, and the failure mode is a column that *almost* lines up. One base rule, with Tailwind's built-in `proportional-nums` as the escape hatch for running prose, gets it right by default. |
| D-99 | The React Flow overrides now read the raw tokens (`var(--panel)`) instead of Tailwind's theme aliases (`var(--color-panel)`) | Not cosmetic, and it fixes a pre-existing bug: `@theme inline` emits **no** CSS custom properties, so the compiled `:root` contains no `--color-*` at all. The overrides referenced `var(--color-panel)` and `var(--color-background)` and were therefore already dead on `main`, silently — the page background was in fact being carried by the `bg-background` utility on the body element. Reading the raw tokens makes them work, and makes them follow light mode for free. Anyone writing plain CSS against these tokens must use the raw names. |
| D-100 | Light values are Primer's light semantic set, paired with the existing dark values, which are Primer's dark set | The twelve dark values already in the file are GitHub's. Taking the light halves of the same system means the two modes are siblings rather than one being a guess at inverting the other, and every foreground token clears 4.5:1 against both `background` and `panel` in both modes (lowest is 4.74:1). In light the surface hierarchy inverts — tinted canvas, white panels — so a card still lifts off the page instead of vanishing. |
